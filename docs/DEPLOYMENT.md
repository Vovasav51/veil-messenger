# Relay та HTTPS

Це інструкція для закритої тестової мережі, **не production hardening**. Код не був розгорнутий публічно під час створення.

## Локальний процес

Relay за замовчуванням слухає `127.0.0.1:8787`. Зберігайте SQLite у каталозі окремого користувача із правами `0700`, файл — `0600`. Не кладіть БД у каталог HTTP-сервера, загальний sync чи Git. Токени клієнтів є bearer-секретами. На сервері зберігається лише їхній хеш.

```sh
python3 dist/veil-relay.pyz --host 127.0.0.1 --port 8787 --db "$HOME/.local/share/veil-relay/relay.sqlite3"
```

Деталі CLI та лімітів — у `server/README.md`. Сервер не є відмовостійким кластером і не перевірений для 10 000 користувачів.

## TLS reverse proxy

Для телефонів потрібен власний домен із коректним DNS і довіреним TLS-сертифікатом. Приклад Caddy-конфігурації наведено в `deploy/Caddyfile.example`. Змініть `veil.example.com` на свій домен. Не запускайте приклад як є. Відкриття портів, домен, VPS і сертифікати потребують окремого налаштування; цей проєкт не змінює ваш firewall чи DNS.

- Relay лишається на loopback; зовні доступний тільки HTTPS reverse proxy.
- Обмеження розміру тіла, часу та конкурентності потрібні на proxy, навіть за наявності application limits.
- Не вмикайте access/request-body/header logs. Якщо ведете журнали reverse proxy, вони є додатковими метаданими; не заявляйте «немає логів».
- Relay не довіряє клієнтському `X-Forwarded-For`. За одним proxy IP-ліміти можуть спільно застосовуватись до багатьох користувачів. Для ширшого тестування потрібен продуманий trusted-proxy/per-account rate limiting.
- Резервна копія relay містить метадані й тимчасовий шифротекст. TTL/ACK не знищать старі snapshots/дискові резервні копії; для MVP не робіть автоматичний cloud backup БД.
- Видалення рядків SQL не є гарантованим secure erase SSD чи зовнішніх backup. Шифрування диска хоста — окремий рівень.

## Два клієнти

1. На обох пристроях вкажіть одну HTTPS-адресу relay.
2. Зареєструйте два різні нейтральні `@handle`.
3. Знайдіть один одного точно за handle, порівняйте повний відбиток ключів незалежним каналом.
4. Надішліть тестовий текст; закрийте/відкрийте клієнти, перевірте офлайн-чергу та відсутність дублювання.
5. Перевірте, що SQLite не містить відкритого тексту повідомлення, а після durable receive + ACK відповідний шифротекст видалено.

**Втрата відповіді на реєстрацію:** сервер уже міг створити акаунт, а клієнт ще не отримав токен. У MVP немає завершеного recovery/idempotent-registration механізму; не регенеруйте identity непомітно. Потрібне явне адміністраторське розв'язання тестового випадку. Це відомий блокер ширшої бети, а не гарантоване відновлення.
