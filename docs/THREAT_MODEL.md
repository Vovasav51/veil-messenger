# Veil MVP: модель загроз і межі

**Статус:** внутрішній інженерний огляд дизайну, не незалежний криптографічний аудит. Фактичні результати збірок і тестів див. у `BUILD_STATUS.md`.

## Що захищаємо

- Текст повідомлень під час проходження через мережу й relay.
- Приватні Signal identity/prekeys, стан ratchet, токен та локальну історію.
- Цілісність доставки під час звичайних збоїв: retry, повторний pull, перезапуск, невдалий запис на диск.

MVP — один пристрій на акаунт, чати 1:1, офіційний libsignal, зашифрований локальний vault, foreground polling. Групи, sealed sender, recovery, cloud backup, push та key transparency відсутні.

## Противники та залишкові ризики

| Противник | Захист / межа |
|---|---|
| Спостерігач Wi-Fi/ISP | HTTPS + Signal шифротекст. IP, обсяг і час трафіку залишаються видимими; TLS перевіряється стандартним системним trust store. |
| Оператор relay | Не має приватних ключів чи відкритого тексту. Бачить sender/recipient, handle, публічні ключі, IP, час і довжину. Може затримати/видалити повідомлення. |
| Зловмисний каталог ключів | Може підмінити перший TOFU-контакт. Незалежне порівняння повного відбитка необхідне, щоб підтвердити ключі. Зміна вже закріпленої identity має блокуватися. |
| Крадій пристрою | OS sandbox, шифрований vault, Keychain/Keystore підвищують захист. Розблокований/зламаний пристрій, root/jailbreak, знімок пам'яті — поза гарантіями. |
| Учасник чату | Може копіювати або фотографувати отриманий текст. E2EE цього не забороняє. |
| Supply-chain атака | Потрібні зафіксовані офіційні залежності, перевірка їх походження та хешів, regression-тести. Сам факт використання libsignal не аудирує Veil. |

**Forward secrecy не стирає збережену історію.** Якщо зловмисник отримав доступ до розшифрованого vault або розблокованого клієнта, старі тексти, які користувач зберігає, доступні незалежно від видалення старих ratchet message keys.

## Відмінності від PDF

- Без телефону не означає анонімність: handle та UID є стійкими ідентифікаторами, UUIDv7 містить час створення (RFC 9562).
- Bearer-auth relay знає відправника. Sealed sender у цьому MVP немає; навіть sealed sender сам по собі не приховує всі IP/часові кореляції та одержувача маршрутизації.
- SQLCipher замінено на атомарний AES-GCM vault; PostgreSQL/Redis — на SQLite; WebSocket/push — на foreground HTTP polling.
- Немає підтвердження навантаження на 10 000 користувачів або зовнішнього аудиту.
- Публічні Kyber prekeys у JSON самі по собі не доводять використання чи повну постквантову безпеку. Див. конкретну інтеграцію й pin libsignal; окремих PQ-гарантій Veil не заявляє.

## Критичні інваріанти реалізації

### Відправлення

1. Одна синхронна локальна транзакція: бібліотечний encrypt → новий ratchet → локальний текст → готовий outbox-конверт.
2. У разі помилки запису відновлюється **весь** попередній стан, включно з криптографічними записами.
3. HTTP надсилається тільки після успішного durable commit.
4. Retry повторює **той самий id і шифротекст**. Нове шифрування при retry зруйнувало б idempotency, просувало б стан зайвий раз і могло б створювати дублікати.
5. `sent` означає прийняття relay, а не прочитання чи навіть отримання співрозмовником.

### Отримання

1. Перевірка адресата, типу, обмежень та закріпленої identity; sender у JSON не є доказом автентичності.
2. Перевірка локального dedup; повтор уже збереженого конверта не розшифровується ще раз.
3. Одна транзакція: decrypt → ratchet → текст → dedup id.
4. ACK лише для успішно записаних ids. При decrypt/save failure ACK не надсилається.
5. Реле гарантує унікальність id в одній inbox, щоб ACK за id не видаляв конверти двох відправників.

### Ключі та контакти

- Клієнти перевіряють підписи prekeys через libsignal і тотожність directory identity ↔ bundle identity ↔ локальний пін.
- Зміна identity не приймається мовчки й не скидає verification.
- Safety number: бібліотечний numeric fingerprint, version 2, 5200 ітерацій; ідентифікатори — lowercase UID UTF-8. Порівнюється повний 60-значний результат, не короткий префікс.
- Relay споживає one-time prekey атомарно; спожитий id не дозволяється завантажити повторно. Пул/ротація мають обмеження MVP.

Типи конвертів звірено з upstream `CiphertextMessageType`: **Whisper=2, PreKey=3, SenderKey=7, Plaintext=8**. Для 1:1 дозволені тільки 2 і 3. Джерело: [libsignal protocol.rs](https://github.com/signalapp/libsignal/blob/main/rust/protocol/src/protocol.rs); перед оновленням перевіряти саме зафіксований release.

## Локальний vault

- AES-GCM із бібліотечним випадковим nonce на кожен запис; жодного фіксованого IV або відкритого fallback.
- iOS: випадковий ключ у Keychain `WhenUnlockedThisDeviceOnly`, файл із `FileProtection.complete`, backup exclusion. Keychain може переживати видалення застосунку; на це не можна покладатися як на account recovery.
- Android: AES-ключ у Android Keystore, credential-encrypted private/no-backup storage; hardware-backed захист залежить від пристрою. Backup/device transfer вимкнені; `FLAG_SECURE` обмежує системні знімки/preview, але не фізичну камеру чи root.
- Токен, keys, тексти не зберігаються в UserDefaults/SharedPreferences, логах чи HTTP cache.
- Пошкодження vault, відсутній ключ або помилка доступу — явна відмова, **не** автоматична генерація нової особи.
- Третя клавіатура, буфер обміну та системна діагностика — окремі канали витоку. Privacy overlay не блокує всі скріншоти на iOS.

## Relay

- Loopback за замовчуванням; для телефонів — окремо налаштований HTTPS reverse proxy. Публічний deployment у цей сеанс не входить.
- Хеші випадкових bearer-токенів; sender лише з auth. Приватні ключі/відкритий текст ніколи не є полями API.
- Обмеження тіл, типів/base64, mailbox, batch, rate limits; атомарні SQLite операції.
- ACK очищає payload, tombstone лишається для retry до TTL; неотриманий payload видаляється за TTL фоновим purge.
- SQL DELETE не гарантує secure erase SSD/WAL/backup. Хостове шифрування диска та політика snapshots — окремі заходи.
- Без application access/body/auth logs; окремо перевірити журнали proxy/OS. Оператор все одно може увімкнути спостереження.
- Втрата відповіді на реєстрацію наразі не має завершеного recovery flow. Ліміти rate limit локальні одному процесу; нема доказу production-масштабування.

## Критерії перед справжньою бетою

- Успішна macOS iOS-збірка та XCTest; Android compile, lint, crypto/runtime tests.
- Два реальні пристрої, включно з iOS ↔ Android: відправка, відповідь, safety numbers, офлайн, restart, duplicate, out-of-order, identity change.
- Перевірки відмов: tampered ciphertext, диск full/save failure, vault corruption, втрата мережевої відповіді, crash біля ACK.
- Перевірки backup, logs, crash data та обмежень фону.
- Для релізу: власний захищений signing key, не debug key; iPhone provisioning/signing; виконання AGPL та умов каналу дистрибуції.
- Незалежний аудит інтеграції криптографії та сховищ до використання для чутливого листування.

**Development APK можна передавати для тестування з явною позначкою debug/unaudited. Це не production-реліз і не доказ безпеки.** Linux не має Xcode/iOS SDK; вихідний ZIP чи симуляторна `.app` не є встановлюваним iPhone IPA.
